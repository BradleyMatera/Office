Project Overview

The goal of this workflow was to automatically capture and store object metadata using a serverless AWS architecture. Instead of manually reviewing uploaded files, the workflow reacts to file uploads, extracts useful metadata, and stores a normalized record for later reference.

The public version of the project highlights architecture, implementation logic, reasoning, documentation style, and cloud cost awareness. It is meant to show real technical work in a recruiter-safe and interview-safe format.

  • Event-driven serverless design
  • Object metadata extraction from uploaded files
  • DynamoDB persistence for normalized metadata records
  • Static presentation layer for documentation and results
  • Transparent usage-based cost thinking

Tech Stack

  • Amazon S3
  • AWS Lambda
  • Amazon DynamoDB
  • CloudFront or Amplify
  • CloudWatch-style operational monitoring
  • HTML, CSS, and technical documentation

Architecture

The workflow is intentionally simple: storage, event trigger, compute, persistence, and presentation. That simplicity is part of the strength of the design.

Processing Workflow

1. Upload

A file is added to an S3 bucket used as the workflow intake point.

2. Trigger

The upload event triggers a Lambda function that handles extraction logic.

3. Extract

The function reads object information and derives structured metadata.

4. Normalize

Metadata fields are shaped into a consistent, queryable record format.

5. Persist

The normalized record is stored in DynamoDB for later viewing and analysis.

6. Present

A static frontend documents the architecture, workflow, and output in an accessible way.

AWS Services Used

Amazon S3

Used as the file intake layer and event source for object uploads.

AWS Lambda

Runs extraction logic without managing servers or provisioning long-lived compute.

Amazon DynamoDB

Stores extracted metadata records in a normalized, low-overhead NoSQL structure.

CloudFront or Amplify

Supports static delivery of the frontend documentation and demonstration layer.

Cost Model

A major part of the project was not just building the workflow, but explaining what drives cost. The public case study keeps that same mindset by breaking the system into measurable usage inputs.

  • S3 storage consumed by uploaded files
  • S3 request activity for object operations
  • Lambda invocation count and execution duration
  • DynamoDB reads and writes
  • Static delivery and transfer considerations

Why it matters

Cost awareness turns a school-style or demo-style project into something closer to real cloud engineering. It shows that architecture decisions have operational consequences.
