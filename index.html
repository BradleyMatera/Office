The problem

Turn file uploads into structured metadata without running a server

The workflow reacts when a file arrives in Amazon S3, extracts current object-level metadata, normalizes it into a documented schema, and stores an idempotent record in DynamoDB. It is intentionally event-driven, low-operations, and measurable.

01

Upload

An encrypted, versioned S3 bucket receives a file and publishes an object-created event.

02

Extract

Lambda validates the event, URL-decodes the key, and reads object headers through HeadObject.

03

Persist

A deterministic record identity and conditional DynamoDB write make repeated event delivery safe.

System design

Simple services with clear responsibilities

S3 owns file intake, Lambda owns short-lived processing, DynamoDB owns metadata persistence, and the monitoring and failure path make asynchronous behavior observable and recoverable.

Real implementation

This is deployable code, not only a diagram

The repository includes AWS SAM infrastructure, a Python Lambda handler, unit tests, a representative S3 event, repeatable developer commands, and GitHub Actions validation.

Infrastructure controls

  • S3 encryption, versioning, and public-access blocking
  • DynamoDB on-demand mode, encryption, and point-in-time recovery
  • Python 3.12 ARM64 Lambda with X-Ray tracing
  • Asynchronous retry and maximum event-age controls
  • Encrypted SQS on-failure destination
  • Log retention and Lambda error alarm
  • Retained bucket and table during stack deletion

Function behavior

  • Validates the S3 event major version
  • Rejects unsupported event sources
  • Decodes S3 object keys correctly
  • Uses version-aware HeadObject requests
  • Normalizes optional headers and checksums
  • Uses deterministic SHA-256 record identity
  • Logs created and duplicate outcomes as JSON

Data contract

Normalized, versioned, and explainable

Each item uses RecordId as the DynamoDB partition key. The ID is derived from the bucket, decoded object key, version ID, and ETag so retries are safe while distinct object versions remain distinct.

Representative DynamoDB itemFull contract
{
  "SchemaVersion": "1",
  "Bucket": "metadata-workflow-uploadbucket-example",
  "ObjectKey": "incoming/quarterly report.pdf",
  "FileName": "quarterly report.pdf",
  "EventName": "ObjectCreated:Put",
  "SizeBytes": 4096,
  "ContentType": "application/pdf",
  "ETag": "0123456789abcdef...",
  "StorageClass": "STANDARD",
  "VersionId": "example-version-id",
  "UserMetadata": {
    "department": "support"
  }
}

Recorded fields

  • bucket and decoded key
  • file name and object size
  • content type and ETag
  • event and processing timestamps
  • storage class and version ID
  • sequencer and user metadata
  • checksum fields when supplied

The function reads object headers. It does not download the full file body.

Operational behavior

Designed for retries, duplicates, and investigation

1

Process

Lambda handles the S3 event and attempts the conditional metadata write.

2

Retry

Unexpected failures are raised so Lambda asynchronous retry behavior applies.

3

Quarantine

An event that still fails is delivered to the encrypted SQS failure queue.

4

Recover

The runbook requires root-cause correction, safe replay, verification, and only then message deletion.

Duplicate delivery

Returns a successful duplicate outcome rather than creating another item.

Partial multi-record failure

Successful records remain stored while the invocation reports the failed record indexes for retry.

Data deletion

The S3 bucket and DynamoDB table are retained instead of being silently destroyed with the stack.

Security and public boundaries

The site is public. The AWS account is not.

GitHub Pages contains documentation, sample events, and source code. It contains no AWS credentials, no direct bucket or table access, no production customer data, and no confidential Amazon implementation material.

Implemented protections

  • Encryption at rest for S3, DynamoDB, and SQS
  • S3 public-access blocking
  • Least-privilege generated policies
  • No object-body logging
  • Documented warning against sensitive user metadata

Truthful claim boundaries

  • No production customer ownership
  • No live enterprise ticket ownership
  • No unrestricted Amazon administration
  • No claim that public files are exact internal files
  • No confidential internship material

Cost reasoning

Measured by usage, not described with a fake universal price

The workflow breaks cost into the inputs that actually change: storage, requests, function duration, database operations, failure traffic, logs, retention, and transfer. Region and account usage still matter.

Deploy it

Build and launch through AWS SAM

Use an AWS account you are authorized to manage. Review the template and CloudFormation change set before creating resources.

1. Validate locally
make install
make lint
make test
make validate
make build
2. Deploy
sam deploy --guided \
  --stack-name aws-serverless-metadata-workflow \
  --region us-east-1
3. Upload a test object
aws s3 cp sample.txt \
  s3://YOUR_UPLOAD_BUCKET/incoming/sample.txt \
  --content-type text/plain \
  --metadata source=pages-demo
4. Verify
aws logs tail /aws/lambda/YOUR_FUNCTION_NAME \
  --since 10m --follow

aws dynamodb scan \
  --table-name YOUR_METADATA_TABLE \
  --max-items 10
Cleanup warning: The upload bucket and metadata table use retention policies. Deleting the CloudFormation stack does not automatically destroy their data.
